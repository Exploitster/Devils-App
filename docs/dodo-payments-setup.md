## Continue after your first four setup steps

### 5. Correct the product price

In your Dodo dashboard, keep **Test Mode** selected. Open Products → your Devils Advocate Monthly product.

- Base currency: **INR**.
- Price: **₹2,000**. If an API asks for the smallest currency unit, that is `200000` paise.
- Payment frequency: **every 1 month**. No annual product.
- No discount or purchasing power pricing. International customers should receive a currency conversion of the INR price, rather than a different regional price.
- No Dodo trial. The app supplies the 24-hour trial without collecting a card; subscribing early starts paid billing immediately.
- If asked for a total subscription lifetime, Dodo's ongoing-subscription setup uses **20 years / 240 months** with monthly payment frequency. This is not a yearly charge or a commitment by the customer to pay for 20 years. Customers can cancel monthly renewal. A total lifetime of just one month would stop after one payment.

If Dodo will not let you change the existing product, create a new matching test product and save its product ID privately in the existing Vercel product-ID setting. Do not change unrelated API keys.

### 6. Enable international currency conversion

Dodo → Settings → Business → **Adaptive Currency** → enable, if available for your merchant account. Keep purchasing power pricing and fixed regional prices off for an INR-equivalent price. Supported currencies, payment methods, taxes, exchange rates and recurring mandates vary. The checkout must disclose the actual amount and renewal terms; do not promise every payment method in every country.

### 8. Connect the payment notification (webhook)

Dodo → Developer / Webhooks → Add endpoint. Use this exact URL **after the new app deployment is confirmed**:

```
https://www.devils-advocate.app/api/billing/dodo/webhook
```

Choose all subscription events, payment events, refund events and dispute events. These notifications keep access in sync after renewals, failed payments, cancellations, refunds and disputes. Save the endpoint.

Copy its **webhook signing secret** privately. Open Vercel → `devils-app` → Settings → Environment Variables → Add:

```
DEVILS_DODO_WEBHOOK_SECRET
```

Paste the Dodo signing secret as its value. Select **Production**, mark Sensitive, and save. This is a new Dodo-specific variable; do not replace your AI, Google, Supabase or Stripe keys. Never send this value through chat or put it in GitHub.

### 10. Rehearse before collecting money

Sign in → Billing → Open test checkout. Use Dodo's documented test payment details. Check:

1. INR price ₹2,000 and an international currency checkout show the intended base price/conversion and taxes.
2. A verified payment appears in Dodo and its webhook delivery returns HTTP 200. Billing → Refresh payment status shows a test subscription.
3. Refreshing checkout does not create duplicate subscriptions. Returning to the app without paying does not confirm payment.
4. Test renewal, failed renewal, customer portal, payment-method recovery, invoices, cancel renewal, refund and dispute. Read back that renewal is canceled.
5. Test access boundaries in an isolated test harness: exactly 24 hours for a cardless trial; expired accounts retain history but cannot generate. Test money must never unlock live paid access.
6. Test account deletion. An uncertain payment or a still-open checkout can leave closure pending. Dodo does not offer an API to expire an existing checkout; never claim future charges are impossible until that checkout is resolved or expired and all subscriptions are verified canceled.

The test checkout itself is genuine provider integration. Automated unit tests use SDK HTTP test doubles and genuine webhook signature verification; they cannot certify your merchant account or your configured product.

## How it works

Verified signup / first verified app login establishes a server timestamp. With paid access enabled, that account gets 24 hours without a card. An expired trial keeps saved history and exports. A customer can subscribe early or later. Checkout requests use the server's single monthly product and server-owned customer, never a client-supplied price/customer. A redirect does not fulfill payment. Signed, deduplicated webhooks reread canonical subscriptions and succeeded payments with a current service period; refunded or disputed periods cannot grant access. Payments in Test Mode remain distinct from live paid access.

Unknown provider write outcomes are held for reconciliation instead of retried automatically, because generic SDK idempotency options do not establish Dodo API idempotency support. This favors avoiding duplicate charges over pretending every failure can be automatically recovered.
